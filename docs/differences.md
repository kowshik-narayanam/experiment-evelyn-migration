# Differences from Evelyn

Every place where the port behaves differently from Evelyn, and why. D-1 to D-12 were approved with the decisions on
2026-10-19 ([decisions.md](decisions.md#differences-these-decisions-create)); D-13 to D-17 were found while porting
(Phases 1-2), and some earlier rows gained detail; D-18 is your answer to Q17. Citations use the aliases of
[mapping.md §0](mapping.md#0-sources-and-how-to-check-a-citation) and are checked by `scripts/check_citations.py`.

| # | Difference | Forced by |
|---|---|---|
| D-1 | Records fan out through two explicit loops, and each record starts its own main-flow instance (`fireAndForget: true`); in Evelyn the records join the running main-BP instance (mapping claim 11) | Maestro has no record streaming (DEC-4) |
| D-2 | `start_bp_uuid` is the CSV flow's run (`$metadata.InstanceId`), not the main flow's. It and `bp_start_time` (a new `csv-monitor-task` output, the UTC time the function starts), `dw_variation` (the job's `UIPATH_FOLDER_KEY`; in a debug run it is the workspace, where the function jobs run, owner's tenant run, 2026-10-19), `dw_version` (the library's version), `model_version` and `provider_id` come from the CSV flow, the job and the library | no WorkFusion task context (DEC-5) |
| D-3 | The configuration is a bucket file read once per job, holding keys Evelyn's payload file lacks; a missing file fails the step | no Digital Worker configuration service (DEC-8) |
| D-4 | S3 paths become keys of one bucket; "bucket exists" means "a key under that folder exists"; three path-string defects are not reproduced. A listing failure raised by the SDK (an HTTP error, a transport error, an unknown bucket) is swallowed into “There are no csv files in …”, as Evelyn's `C:service/S3DownloadService.java:87` “} catch (SdkClientException e) {” swallows AWS errors; in AWS SDK v1 service errors are `SdkClientException`s too (`javap` on aws-java-sdk-core 1.12.792 from `~/.m2`; the deployed version is **Inference**). Any other Python error propagates. A download of a missing key fails with `FileNotFoundError` “Please provide correct path to file: <key>” before any download (DEC-7); in Java the AWS download itself fails, with the AWS SDK's text (`C:service/S3DownloadService.java:104` “s3Service.getAmazonS3().download(”; **Inference**, not run) | buckets are not S3 (DEC-7) |
| D-5 | Data Fabric schema: PascalCase names; each table's `uuid` column is `TransactionUuid`, `AlertUuid` or `HitUuid`, because Data Fabric refuses the field name `Uuid` (“Field name for 'Uuid' is a reserved SQL word and cannot be used as an entity or field name.”, owner's tenant run, 2026-10-19); `MULTILINE_TEXT` capped at 10,000, UTC times, booleans for `autoQC`/`ticker`, none of Evelyn's ten non-unique indexes | Data Fabric's types and rules (DEC-6) |
| D-6 | The three writes are separate calls; in Evelyn the alert and hit writes were one database transaction | Data Fabric has no transaction across calls |
| D-7 | A rerun does not duplicate hit rows | the prompt asks for it |
| D-8 | Records travel as objects. Not reproduced: JSON text details (nulls, HTML escaping, key order), Java's `HashMap` order of aliases, dates, locations, maps and the parse-error list (file order instead), Java exception class names in front of messages, Java `UUID` objects (uuids are lower-case text). `csv-task`'s rows always carry all four keys (`screened_data`, `wle_list`, `request_id`, `stop`), null when unused; Evelyn's rows carry only their own (`J:task/csv/CsvTaskProcessor.java:72` “.put(SCREENED_DATA, gson.toJson(entry.getKey()))”). Header and format-file names are lower-cased with Python's `lower()`; Java's `toLowerCase()` uses the worker's default locale (`J:task/csv/service/CsvDataService.java:158` “e.getKey().toLowerCase().trim()”), assumed English (**Inference**). Bytes that are not UTF-8 become U+FFFD in both, but not always as many: an encoded surrogate (CESU-8, the three bytes `ED A0 80`) gives three U+FFFD in Python (`BucketStore.read_csv_text` and `read_text`, `errors="replace"`) and one in Java (`C:service/S3DownloadService.java:125` “CSVParser.parse(new String(s3ContentBytes),”, run on JDK 21, where the default charset is UTF-8) | no Gson, Jackson or Java in the path |
| D-9 | Logs go to the job log, not Control Tower's event log, with Evelyn's texts verbatim. Two warnings are the port's own: a swallowed listing failure (D-4) and an unreadable configuration file (D-14) | platform |
| D-10 | The CSV BP's "Final Results" step exports the run's records; the Flow's End node does nothing | no equivalent; nothing in the slice reads it |
| D-11 | `csv-task` runs on the default robot (1 GB, 15-minute cap: `L:KT/coded-functions.md:122` “15-minute hard cap per job; 1 GB memory by default.”), not Evelyn's 4 GB high-memory worker | robot size is set after deploy; the mock files are small |
| D-12 | A failing file is caught by `csv-task`'s error port and the CSV flow goes on to the next file; the failure shows on the node, not as a failed record (Q16) | a Maestro incident would suspend the whole run |
| D-13 | Dates are parsed by the library's own parser for the patterns of Evelyn's date-format table, not by `SimpleDateFormat` (`S:DateUtils.java:125` “new SimpleDateFormat(format.format(), Locale.ENGLISH)”, non-lenient: `S:DateUtils.java:126` “setLenient(false)”). It matched the JDK on all 115 date texts in the library's tests. Not reproduced: a date that does not exist in the worker's time zone (for example 30 Dec 2011 in Pacific/Apia) | no Java in the path |
| D-14 | The configuration reader takes plain dotted keys only, not JsonPath expressions; an unreadable JSON file gives an empty configuration (as in Java) plus a warning; an object value is not rendered as Java's `{c=1}` text. Evidence: `JsonStringConfiguration.java` in the jnw-toolkit 3.0.0.87 sources jar (lines 47, 73, 105) | no JsonPath in the path; the slice reads five plain keys |
| D-15 | Only a lost insert race on `TransactionUuid` counts as "transaction '<uuid>' already exist"; Evelyn swallows any integrity error on save (`J:service/TransactionService.java:75` “} catch (DataIntegrityViolationException ex) {”), for example a null client id, which fails the step here. It cannot happen on the CSV path, where `clientId` defaults to "1" | Data Fabric reports refusals differently from JPA; swallowing every refusal would hide real failures (DEC-6) |
| D-16 | Two Java failure paths are not reproduced. A key like `input_address__country` throws an index error in Java (`S:LocationUtils.java:90` “.split("_")[0])”); the port returns "". `csv-task` does not wrap parse failures as “S3 file content can not be parsed” (`C:service/S3DownloadService.java:136` “S3 file content can not be parsed: ”): with commons-csv `EXCEL` as configured (`C:service/S3DownloadService.java:126` “CSVFormat.EXCEL.builder()”) no text raised it in the csv-task agent's comparison with commons-csv 1.14.1 on 56 inputs (**Inference** that it cannot fire) | translating dead or crashing paths would add code no test can reach |
| D-17 | Function inputs. A Flow node sends every input it declares, so: (a) a key missing from a job's input is refused by the runtime's schema check before `main` runs, without the step text; Java fails inside the step (`J:task/csv/CsvSchemaProducerProcessor.java:47` “gson.fromJson(input.getData().get(WLE_LIST).toString(), listType)”); (b) a null `wle_list` fails the producer before any write, where Java writes the transaction and the alert and then fails (`J:service/AnalyticsService.java:65` “if (wleDataList != null) {”, then `J:task/csv/CsvSchemaProducerProcessor.java:60` “.putValue(WLE_COUNT, wleDataList.size())”); (c) `rest_request` counts as absent when null, "" or {}, where Java tests for the key (`J:task/csv/CsvSchemaProducerProcessor.java:49` “!input.getData().containsKey(RestRequest.REQUEST_FIELD_NAME)”); (d) four error texts are the port's own: “Required input 'screened_data' is missing or empty”, “Required input 'wle_list' is missing (an empty list is allowed)”, “bp_start_time is empty: …” and “bp_run_id is empty: …”, each inside “Exception was thrown by Evelyn NSS step csv-schema-producer: …” | Flow nodes send every input (DEC-3); the run-context inputs are new (D-2) |
| D-18 | A child run that fails to start is caught by the "NSS-main-BP" call node's error port and the record loop goes on to the next record; the failure shows on the node (`nssMainBp1.error`). In Evelyn an error answer to the BP call fails that record's step (mapping claim 11). With `fireAndForget: true` the port sees only a failure to start; a child that faults later shows only in its own instance (DEC-4) | a Maestro incident would suspend the whole CSV run (Q17) |
